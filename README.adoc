= Windows Container View

View and control the graphical user interface of a Windows container.

image::Docs/screenshot.png[]

A Windows container has no display adapter, so a GUI application running in one
has nowhere to draw. This tool gives it somewhere: the client, running inside the
container, builds a window station and desktop, paints every window into a bitmap
through `WM_PRINT`, and sends the result over RPC to a server on the host, which
displays it in an SDL window and sends mouse and keyboard input back.

It is for **process-isolated containers only** (`--isolation process`).

== Requirements

* Windows 10 or later, or Windows Server, x64
* Visual Studio 2019 or later, with the Desktop development with C++ workload
* Docker, to run the container

Building produces two programs, `Sandbox-Server.exe` and `Sandbox-Client.exe`.

== Building

Open `Sandbox.sln` and build `Release|x64`, or from a command line:

[source,powershell]
----
msbuild Sandbox.sln /p:Configuration=Release /p:Platform=x64 /t:Build /m
----

Both land in `Output\x64\Release\`. `Sandbox-Server.exe` needs `SDL2.dll` and
`SDL2_image.dll` beside it, which the build copies. `Sandbox-Client.exe` needs
nothing but system DLLs.

== Running

. Run `Sandbox-Server.exe` on the host. A window appears and waits for the
client. It takes no arguments.

. Run a container with `Sandbox-Client.exe` mounted into it. The host address
comes from `SANDBOX_HOST`; the port defaults to 5001 and can be changed with
`SANDBOX_PORT`.

+
[source]
----
docker run --rm -ti --isolation process ^
  -e SANDBOX_HOST=192.168.1.50 ^
  -v C:\path\to\Sandbox-Client.exe:C:\Sandbox\Sandbox-Client.exe:ro ^
  mcr.microsoft.com/windows/servercore:ltsc2025 ^
  C:\Sandbox\Sandbox-Client.exe
----

. The window on the host shows the container's desktop.

`SANDBOX_HOST` is an address of the machine running `Sandbox-Server.exe` that the
container can reach: the container's default gateway if both are on the same
machine, or the host's address on a network the container can see.

The image must be **Server Core** or later; Nano Server removes Win32k and cannot
create windows. Its build must match the host's, or process isolation will refuse
to start.

=== Choosing what to run

Anything after the program name is started on the container's desktop. With
nothing, `cmd.exe` is started:

[source]
----
C:\Sandbox\Sandbox-Client.exe notepad.exe
C:\Sandbox\Sandbox-Client.exe "C:\Program Files\App\app.exe"
----

=== Configuration

Everything is an environment variable.

[cols="1,1,3"]
|===
| Variable | Default | Meaning

| `SANDBOX_HOST`
| none
| Address of the server. Required by the client.

| `SANDBOX_PORT`
| `5001`
| RPC endpoint. Must match on both sides.

| `SANDBOX_RESOLUTION`
| `1024x768`
| Container desktop size, `WIDTHxHEIGHT`. The container has no display adapter, so
only the modes its stub display driver advertises are accepted; anything else
falls back to the default. See `Docs/BUILD.md` for the list.

| `SANDBOX_DOCK`
| none
| Set to `1` to draw the dock — a strip of window buttons — below the desktop,
so a minimized window can be brought back.

| `SANDBOX_FPS`
| `30`
| Capture rate. The per-frame cost is roughly fixed, so this trades container CPU
for smoothness.

| `SANDBOX_DEBUG`
| none
| Set to `1` to print anything at all.
|===

=== Output

Neither program prints anything by default. Set `SANDBOX_DEBUG=1` on either side
to see what it is doing; the client then prints a per-second breakdown of where
each frame's time goes.

== How it works

`PrintWindow()` writes a window's appearance into a device context, but only for
windows on a window station that allows I/O — `WinSta0`. Anywhere else the result
is black. Container processes start on the service window station
(`Service-0x0-xxx$`), where the access rights are also too low to switch desktop
or create windows at all.

So the client, before doing anything else:

. Grants everyone full access to the `WinSta0` window station and the
`WinSta0\Default` desktop.
. Assigns itself to `WinSta0` and sets its thread's desktop to `WinSta0\Default`.
. Starts the requested program on that desktop, so its windows are ones the
client can see and send input to.

From then on it loops: paint every window into one bitmap, encode it as PNG, and
send it to the host in a single RPC call that also carries back whatever input
arrived. Frames whose pixels are identical to the previous one are not sent.

A minimized window has no pixels to paint, and a container has no shell, so there
is no taskbar to bring it back from — it would simply be gone. With
`SANDBOX_DOCK=1` the client draws one: the dock, a strip of window buttons along
the bottom of the desktop. Clicking a button restores that window and brings it
forward; clicking the button of the window already in front minimizes it.

The dock behaves the way a taskbar does, in both directions. It is drawn over the
bottom of the desktop, so the frame is exactly the screen and the host's window
is the same size either way. And the client narrows the container's work area by
the dock's height, so a maximized window stops above it: the container sees a
smaller usable area, not a smaller screen. The host is not told any of this.

The cursor is not painted into that bitmap. It travels separately and the host
composites it, because a cursor baked into the frame makes the pixels underneath
it dirty every time the mouse moves.

== Known limitations

* **No authentication.** The server registers with
  `RPC_IF_ALLOW_CALLBACKS_WITH_NO_AUTH`, so anything that can reach the port can
  read the picture and inject input. Suitable for a trusted network only.
* **One session at a time.** The server's state — texture, cursor, event queue —
  is global.
* **Input is applied at the frame rate.** The pointer, the wheel and the keyboard
  all travel back with the frame, so they take effect at `SANDBOX_FPS` rather than
  the moment they happen.
* **Themes draw imperfectly.** With no DWM in the container, `WM_PRINT` does not
  fully support themed controls. Status bars are handled by re-printing each
  descendant; dialog buttons still flicker on a fraction of frames.
* **Every window keeps its resize border.** DWM normally hides it. Without DWM,
  `WM_PRINT` paints all 8 pixels of it as a visible frame, and it cannot be
  removed without removing the title bars with it.
* **Capacity.** About 30% of one core per container on an idle desktop, and about
  one core with a dialog open.
* **No audio.** Containers have no audio endpoint and no stream to capture.
* **NAT hides the source address.** Docker's NAT rewrites container traffic, so
  the server cannot tell containers apart by address.

== Epilogue

This is a proof of concept, for educational and research purposes: even a headless
container can be made to yield visual information.

Use cases it fits:

* Installing software in a container that needs a user to click through it —
  a GUI installer, a licence key — and exporting the container afterwards.
* Driving a service that requires user interaction through session 0.
* Testing a suspicious program in a lightweight sandbox.
* Serving as the display half of a sandbox technology that spawns processes in
  Server Silos and retrieves their output, the way Windows Defender Application
  Guard does for Edge.
